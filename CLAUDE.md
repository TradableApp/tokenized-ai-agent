# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Token-gated AI agent: contracts on Base, and an oracle that runs in an Oasis ROFL TEE (Runtime OFf-chain Logic; the ROFL app is registered on Sapphire, where ROFL apps live). The `Sapphire*` contracts are a community example for Oasis Sapphire, kept in parity with their own idioms; no deployment of them is planned.

> `simple-tokenized-ai-agent` is a deliberately simpler public reference implementation; this repo is the primary codebase.

## Two-Layer Project Structure

This repo is **two separate Node.js packages** with different concerns:

- **Root** (`package.json`): Hardhat project — Solidity contracts, deployment scripts, tests
- **`oracle/`** (`oracle/package.json`): Node.js oracle service — event listener, AI routing, storage, off-chain logic

Always `cd oracle/` and run `bun install` separately when working on oracle code. Contract ABI artifacts (from `bun run compile` at root) are consumed by the oracle via `../../artifacts/contracts/`.

## Shared schema submodule

The oracle reads/writes to a shared GCP Cloud SQL Postgres instance with `sense-ai-core`. Table definitions + migrations live in [`TradableApp/sense-ai-shared-schema`](https://github.com/TradableApp/sense-ai-shared-schema), pulled in here as a git submodule at `packages/shared-schema/`.

```bash
# First clone:
git clone --recurse-submodules https://github.com/TradableApp/tokenized-ai-agent

# After a regular clone:
git submodule update --init --recursive

# Pulling latest schema updates:
git submodule update --remote packages/shared-schema
git add packages/shared-schema && git commit -m "chore: bump sense-ai-shared-schema to <version>"
```

It is a path dependency of the oracle (`oracle/package.json` → `"../packages/shared-schema"`, imported as `@tradableapp/sense-ai-shared-schema`), so both apps stay in lockstep on table shape and migration history.

## Architecture

### Dual Contract Families

Two parallel contract families exist, one per chain. SenseAI runs on the EVM family on Base; the Sapphire family is a community example kept in parity with its own idioms:

| Family | Chain | Contracts |
|--------|-------|-----------|
| Sapphire | Oasis Sapphire | `SapphireAIAgent`, `SapphireAIAgentEscrow` |
| EVM | Base | `EVMAIAgent`, `EVMAIAgentEscrow` |

Both families expose the same event interface (`PromptSubmitted`, `RegenerationRequested`, `BranchRequested`, `MetadataUpdateRequested`) so the oracle handles them identically after initial detection. The key difference is the encryption model (see below). Contracts use OpenZeppelin upgradeable patterns.

### Encryption Model: Sapphire vs EVM

The oracle has two distinct encryption paths, selected automatically by `contractUtility.js`:

- **Sapphire**: The chain's TEE encrypts all calldata at the protocol level. Event payloads arrive as encrypted strings. The oracle decrypts them with the session key carried in the event payload.
- **Base (EVM)**: No protocol-level encryption. The oracle uses ECIES (`eth-crypto`) to decrypt an asymmetrically encrypted session key, then AES-256-GCM to decrypt the conversation payload client-side.

`contractUtility.js:initializeOracle()` detects which mode applies by checking the network name and wraps the ethers provider/signer with Sapphire helpers when needed.

### The Oracle's Own Keys (`oracle/src/oracleKeys.js`)

The oracle has two keys: one signs its transactions, the other decrypts the session key of each prompt. Where they come from follows from `NETWORK_NAME` alone, with no setting to choose:

- **A local network** (`base-localnet`, `sapphire-localnet`): both are `PRIVATE_KEY`.
- **Every other network**: both are made by the ROFL key service (`POST /rofl/v1/keys/generate` on the appd socket), under two key ids that hold the chain id and the agent address. The same app and id always give the same key, so nothing is stored. `PRIVATE_KEY` must not be set there: `startupConfig.js` refuses to start if it is. If the key service does not answer, the oracle waits, alerts after two minutes and then hourly, and uses no other key.

`index.js` obtains the keys, then calls `configure(keys)` on `aiAgentOracle.js`, then `start()`. Nothing is built while the module loads. The rest of the oracle receives a `decryptor` (`publicKey`, `decrypt`, `proveKey`) and never the key itself. The key ids are pinned by `oracle/test/oracleKeys.test.js`; changing one changes the oracle's address and its encryption key.

Both keys are registered with `oracle/src/secretValues.js` when obtained, and removed by value from everything the console prints and everything sent to Sentry. A new call to the appd socket that returns key material must go through the quiet request helper in `roflUtility.js`, which never repeats an answer.

### Oracle Event Flow (`oracle/src/aiAgentOracle.js`)

The main orchestration file. High-level flow on each contract event:

1. Event lands in `pollEvents()` → pushed to `p-queue` (concurrency 5)
2. `handleAndRecord()` wraps each handler — catches validation errors to silently drop malicious payloads, queues retryable failures in the state store for retry. It never saves the chain cursor — the scan loops do, once a whole batch is handled
3. Handler (`handlePrompt`, `handleRegeneration`, `handleBranch`, `handleMetadataUpdate`) decrypts payload, validates via Zod (`payloadValidator.js`)
4. `reconstructHistory()` fetches prior messages from decentralized storage using the linked-list `parentCID` chain, within the walk's limits (below, "Reading stored files"); raw encrypted strings are cached in an LRU cache (100k items and 128 MiB, 24h TTL) once they decrypt and read as a message file, to avoid redundant fetches
5. `queryAIModel()` routes to the AI tier (see below)
6. Response is encrypted and new storage files created via `formatters.js`, uploaded to Autonomys or Irys
7. Oracle submits the answer through the contract with its ethers signer (wrapped with the Sapphire helpers on a Sapphire network). Only the Sapphire app's own oracle registration at start-up goes through `roflUtility.js:submitTx()` (ROFL appd socket)

Sequential transaction submission is enforced by `txMutex` (async-mutex) to prevent nonce collisions.

**Live reasoning frames (`oracle/src/stream/`).** Each run of a prompt or regeneration (first processing, retry, restart) gets an answer stream once its session key is known (`openAnswerStream` → `createAnswerStream` in `answerStream.js`). The stream builds the frames of the contract in `streamContract.js` (version 1, shared with the dApp's `src/lib/liveReasoning/contract.ts` and held equal by the shared test vectors, held as data in `oracle/test/fixtures/streamVectors.json` and checked by `oracle/test/streamContract.test.js`, one per frame type with the fixed key, an IV of its own and a fixed plaintext, each rebuilt, encrypted byte for byte, decrypted and checked against the contract; both repos pin the same SHA-256 of the vectors' canonical form (JSON, keys sorted at every level, no whitespace; `STREAM_VECTORS_SHA256`, pinned in the test file and not in the fixture, the dApp's in `vector.testdata.ts`), and there is no cross-repo CI check, so change both repos, the vectors and the hash together): `reset` (seq 0 of every run, `start`, or `retry` when this process has run that answer before), `sources` (once per attempt, before its first step), `step`, `attempt` (a fallback tier entered: Tradable → ElizaOS → ChainGPT → direct Gemini; earlier steps stay), `answer` (only after this run's `submitAnswer` receipt; when waiting for the receipt throws, the transaction this run sent is read by its hash, and a receipt with status 1 makes it this run's answer as if the wait had returned (answer frame, `done answered`, the answer activity); anything else, and every `JobAlreadyFinalized` revert, goes to the handler's catch unchanged; `text` is the exact `answerText` stored, with the uploaded CID; left out over 64 KiB, or when the CID is over `LIMITS.answerCidChars` (128) or not of `[A-Za-z0-9_-]`) and `done` (`answered`, `abandoned` for cancelled, finalized or bad input, `interrupted` for an error that goes to the retry queue). Each frame is sealed with the prompt's session key by `encryptSymmetrically` (`frameCrypto.js`, the one encryptor the stored files use too) and handed to a sink, which gets an expected proof of key (`streamProof`), never the key. The sink is the no-op sink until the stream server below is set with `setStreamSink`. **What is stored is what was streamed:** an assistant MessageFile takes its `reasoning`, `sources` and `answerAttempt` only from `stream.record()`, the projection of the frames built (each item carries its `attempt`; `answerAttempt` is the highest attempt any frame built carries, which is the attempt current when the answer was produced, since the record is read once the answer is in and no attempt frame is built after it; it is written only above 1, so a file with no fallback is unchanged, and a reader treats a missing one as the highest attempt among the items), and nothing reads the model's own reasoning past the stream (`oracle/test/streamSingleSource.test.js`). A thought is sanitised once, before it is streamed or stored (`thoughtSanitizer.js`: fence tags out, tool payloads and the tool plugin's failure thoughts dropped, at most 32 KiB handed to the Brain's `sanitizeOutboundText` (its cost grows with the square of the length and cannot be interrupted) within 2 s, capped at 4000 characters after; anything doubtful is dropped), and turned into a step by `stepFromThought` (`answerProvenance.js`), the one conversion, from the thought itself and not from the run's record, so a step whose sanitising finishes after the ElizaOS run completed is still kept; a thought that arrives after its run ended is not. Limits (20 sources, title and url lengths, 64 steps per attempt, 120/4000 characters, 16 KiB per frame) are applied before the frame is built, so the stored copy is cut the same way. The `answer` frame is the one exception to the 16 KiB frame limit: its text is limited to 64 KiB of UTF-8, and JSON escaping can grow that up to six times (a control character becomes `\u00XX`), so it is built against `LIMITS.answerFramePlaintextBytes` (6 × 64 KiB + 1 KiB = 394,240; the frame's other fields are at most 429 bytes with a 128-character CID). `sealedFrameChars` gives the length of a sealed frame and `MAX_SEALED_FRAME_CHARS` (525,693) the longest: a stream server and the dApp must carry a frame of that size, and the dApp refuses one over it, or over its plaintext limit, before parsing. **Streaming must never delay or lose a paid answer:** no stream method throws; sink calls are guarded and never awaited; each piece of queued work starts when it is queued and is cut off 2.5 s later (above the sanitiser's 2 s), and only its result waits for the work before it, so `flush()` waits at most that plus a 500 ms margin (3 s), however many thoughts are queued; the handler's one flush before `record()` is the wait; a frame is sealed before it takes a seq, so a seal that fails leaves no gap; a stream that cannot be built is replaced by an offline one that still builds the record. Nothing in `stream/` logs an id, a key or model text. The heartbeat carries `stream: { framesBuilt, sinkFailures, sealFailures, buildFailures, thoughtsDropped: { timeout, unavailable, refused, failed, late } }` (`buildFailures`: queued work whose result could not be applied, neither sent nor stored; the sink is closed after `done` even when the done frame could not be sealed): a dropped thought costs the answer nothing, so it is counted by kind, and every kind but `refused` (the sanitiser doing its job) is alerted once per process and at most hourly after (`thoughtDropAlert.js`). The sanitiser is loaded at start-up, not awaited; a failed warm-up is logged by kind and does not stop the oracle. Mock mode's `__E2E_REASONING__` goes through the same tap; `__E2E_STEP_MS__:<n>` spaces its steps (cap 5 s) and `__E2E_RERUN__` ends a prompt's first run after its sources and first step (`done interrupted`) and runs it again in-process once, as a second run opening with `reset retry`. `ORACLE_REPLICA_ID` (1–32 of `[a-z0-9-]`, otherwise 8 random hex chosen at boot; a malformed value stops start-up) is the frames' replica. **Deploy order:** stored files carry every attempt's steps and sources once this is deployed, and a dApp that does not group them by `attempt` shows a failed tier's steps and sources as the answer's own (the file is immutable); so a network's hosted dApp with the live reasoning overlay ships before, or together with, an oracle that stores attempts.

**Live reasoning stream server (`oracle/src/stream/streamServer.js`, `frameBuffer.js`, `streamConfig.js`).** `index.js` starts it before `oracle.start()` and sets it as the sink, so every run's frames reach it. It is a `node:http` server on `STREAM_PORT` (8787) and `STREAM_HOST` (an IP address; unset, every interface, which the container's published port needs; the localnet harness sets `127.0.0.1`), the only port any compose file publishes (`oracle/test/composePorts.test.js`; TLS is the ROFL proxy's). Routes: `GET /stream/{answerMessageId}` (optional `?mode=poll`) with the `X-SenseAI-Stream-Proof` header and an optional `Last-Event-ID` (`<run>.<seq>`); `GET /health` → 200 `{"ok":true}` with `Cache-Control: no-store` (it shows the stream server is listening, not that prompts are answered: the server starts before `oracle.start()`); `OPTIONS /stream/…` for the CORS preflight; anything else → bare 404. Refusals are `{"error": …}` with the status, word and Retry-After from `STREAM_REFUSALS` in `streamContract.js` (400 malformed id, proof, query, a request with a body or a target over 128 characters; 403 wrong proof; 404 not open, Retry-After 2; 410 finished and dropped; 429 too many readers of the answer, or too many full replays of its run, Retry-After 5; 503 the buffer could not hold it, too many readers in all, or shutting down, Retry-After 10). The proof is compared in constant time with the one the answer path computed, before anything about the answer's frames is written; whether the answer is open, finished or has no room (404, 410, 503) is answered before it, by design (the dApp needs it to retry, and answer ids are public on-chain). The server never holds a key. A 200 is `text/event-stream; charset=utf-8`, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`: `retry: 2000`, then the current run's frames from seq 0, or after `Last-Event-ID` when it names the current run, each as `id: <run>.<seq>`, `event: frame`, `data: <iv.ct>`; then live frames (a new run's frames follow on the same response, its first is a reset), `: ping` every `STREAM_HEARTBEAT_MS`, and the end after `done` or at `STREAM_MAX_CONN_MS`. Poll mode ends after what is buffered, or after the first new frame, or after 20 s. CORS: only an origin in the allow-list is echoed (`Access-Control-Allow-Origin`, `Access-Control-Expose-Headers: Retry-After`; preflight `GET`, `X-SenseAI-Stream-Proof, Last-Event-ID`, max age 600; no credentials); `Vary: Origin` always. The allow-list is `STREAM_ALLOWED_ORIGINS` (exact origins, `https:` except loopback) or, unset, by `NETWORK_NAME`: `base-localnet` the dApp's dev server on 3002, `baseSepolia` the sandbox hosting site, `base` production; Firebase Hosting serves each site on `<site>.web.app` and `<site>.firebaseapp.com`, and both are listed; other networks none. An origin left out fails silently: the browser refuses the response and the dApp retries it as a network error, showing and reporting nothing. `frameBuffer.js` keeps each answer's current run (replaced by a new run), drops a finished answer after `STREAM_GRACE_MS` and leaves a 10-minute tombstone (410) for an answered or abandoned one, none for an interrupted one (a retry may follow); caps 1 MiB per answer (room for the contract's largest frame, `MAX_SEALED_FRAME_CHARS`, beside the rest of its run), 64 MiB in all and 512 answers; a frame that is not in the sealed shape or is longer than `MAX_SEALED_FRAME_CHARS` (the contract's `isSealedFrame`) is refused and counted; finished answers dropped first to make room, otherwise the answer is unavailable (503) until its next run. Replays: each run of an answer may be replayed in full `REPLAY_LIMITS.maxCountedReplays` (8) times (`claimReplay` in `frameBuffer.js`); a replay of at most `freeTailBytes` (16 KiB), a reconnect that needs only the tail, is never counted or refused, and a new run counts from zero; past the limit the request gets 429 busy. A replay is written `REPLAY_SLICE_BYTES` (64 KiB) at a time with the event loop let run between slices, frames that arrive meanwhile are held and sent after it, and a slice that throws ends only that reader. Readers: at most `STREAM_MAX_CONN_PER_ANSWER` per answer and `STREAM_MAX_CONN_TOTAL` in all; one whose socket has not drained 10 s after a refused write, or that has more than one run's worth of bytes queued (`readerQueueCap`: the longest run's replay with its SSE lines, about 1.015 MiB, so about 203 MiB for 200 readers at worst), is destroyed, and the sink never waits on a socket. Node's own socket limits (`httpLimitsFor`): `maxConnections` is a descriptor budget, `SOCKET_BUDGET` in `streamConfig.js` (768: an assumed limit of 1024 less 256 kept for the oracle's own sockets; a socket past it is closed on arrival, before any parsing, and counted), not the reader cap, and `STREAM_MAX_CONN_TOTAL` may be at most a third of it (256); every answer but an admitted stream (refusals, preflight, `/health`, unknown paths) sends `Connection: close` and loses its socket; headers (nothing sent included) within 5 s checked every 0.5 s (so at most 5.5 s); 31 requests per socket; keep-alive 3 s (+1 s Node buffer); none of them cuts a live event stream. No per-address limit, on purpose (the reader's address is never read; behind the proxy callers may share one). No compose file has a healthcheck, so a full pool cannot get the oracle restarted; a later healthcheck must not use the public port. The container's descriptor limit and the ROFL proxy's own connection limits are unknown, so the Phase 0 load check measures both and includes an unauthenticated flood and a valid-proof replay loop (`docs/BASE_TESTNET_DEPLOY_RUNBOOK.md` 5.1, which also gives the deploy order and how the stream is reached through the ROFL proxy). Every server failure is counted and each kind logged at most once an hour; the server's stats (readers, refused sockets, failures, answers and bytes held, refused opens and frames) ride in the heartbeat as `stream.server`. On SIGTERM it ends every response within 2 s and raises the signal again; outside a container that ends the process, but in the container node is PID 1 with no `init:`, so the raised signal is ignored and the oracle answers on with the stream closed until SIGKILL (as it did before the handler). Settings (all optional, defaults in code): `STREAM_ENABLED` (`true`; `false` opens no port, sets no sink and adds no signal handler: frames are still built and the record is unchanged), `STREAM_PORT` (8787), `STREAM_HOST` (unset), `STREAM_ALLOWED_ORIGINS`, `STREAM_GRACE_MS` (120000; the dApp assumes this default as a constant, so changing it needs the dApp's constant changed too), `STREAM_HEARTBEAT_MS` (15000), `STREAM_MAX_CONN_MS` (240000), `STREAM_MAX_CONN_PER_ANSWER` (4), `STREAM_MAX_CONN_TOTAL` (200, at most 256); a set value that cannot work stops start-up naming the setting, never its value (`validateConfig`). A port that cannot be had is logged by kind and the oracle answers without a stream. No request is logged, and no stream module puts a reader's address, a header value or an answer id in a log line or an error (`oracle/test/streamLogging.test.js`).

**Errors in logs, alerts and reports.** The error ethers throws for a failed request carries the request's address in its message, and a provider's address holds the account's access key. So in every source file under `oracle/src` (each JavaScript file, and the ElizaOS plugin's TypeScript under `oracle/src/elizaos/plugins/plugin-senseai/src`, which runs in the same TEE; tests, `node_modules`, `dist`, type declarations and the plugin's build script `build.ts` are skipped; its JavaScript under `scripts/` is read), read by `oracle/test/describedErrorsGuard.test.js` without a list, an error caught in a `catch` block, a `.catch` callback or a `.then` rejection handler (an arrow or a `function`), or arriving as the first parameter of a handler for an error, rejection or exception event (`.on`, `.once`, `.addListener`, `.prependListener`: the process's crash handlers among them) or of a hook property whose name speaks of a failure (`onRetry`, `onError`, `onAlert`, `onLost`, `onUnavailable`, …), is never handed whole, nor spread (`{ ...error }`), to the console (`dir`, `assert` and `group` included; with `.`, `?.` or a name in brackets), a logger (`this.logger`, `elizaLogger` included; `success`, `verbose` and `progress` too), `process.stderr.write`, an alert or a thrown error, a settled promise's `.reason` never reaches a sink other than a throw, and no sink is itself the callback (`.catch(console.error)`, `.catch(this.logger.error)`, `.then(ok, console.error)`); the guard does not see an error copied to another name or wrapped in a new one held in a variable, a destructured parameter, a named handler defined elsewhere (`.then(task, task)`), the console under another name or a sink it does not list, and `Sentry.captureException(error)` is deliberately not a sink because every event is cleaned before it is sent (below); only a bare rethrow, or `cause:` in a thrown error, passes it on to code that branches on it. A caught name with a TypeScript type (`catch (error: unknown)`, `(e: Error) =>`) and an optional logger call (`logger.warn?.(…)`) are read too, and the guard is shown to fail on a raw print planted in any file it reads. The plugin describes its errors with `describeError` from its `utils/errorDescription.ts`, which uses the oracle's own describer handed over at load (`setErrorDescriber`, called in `aiAgentOracle.js`) and, before that, gives an error's kind only; it does not bundle the oracle's module. Where an error's message can quote user text or a wallet (a database write of a row, the outbound sanitiser, the payload validator) only its kind is kept (`errorKind`). A configuration problem names the setting and never its value (`oracle/src/startupConfig.js`); a misspelt `NETWORK_NAME` or `STORAGE_PROVIDER` is answered with the one supported name at most two letters away (`closestSupported`). A payload that fails validation names up to five failing fields and the kind of each failure, from the schema, never what was received. The intent classifier logs a prompt's length, never its text. `oracle/test/describedErrorPrints.test.js` and the plugin's `src/__tests__/describedErrors.test.ts` run each module with an error carrying a keyed address and check what is printed, alerted or thrown. `describeError(error)` gives the line of text (`oracle/src/errorDescription.js`): a provider error's `code: shortMessage`, a model provider's error (AI SDK `AI_…`) as its name and status only, any other error's message with its code in front when the message does not name it; then `describedText` cuts the raw text to `MAX_RAW_INPUT` (4096, back to the last space, so the token the cut falls in goes; when that leaves nothing, the line is `[value removed]`) before any pattern runs, keeps the first line that is not blank, drops a failed query's text and bound values (`Failed query: … params: …` is `Failed query`), removes addresses, configured secrets and network peers (`withoutAddresses`), quoted values, bearer tokens, JWTs, base64 runs of 32 or more, wallet addresses and other long hex (a four-byte selector is kept; a database identifier is kept too: a plain lower-case name of at most 63 characters, schema-qualified as `"a"."b"` or `"a.b"` or not, in double quotes right after relation, column, table, constraint, index, type, function or schema, so `relation "failed_jobs" does not exist` and `column "x" of relation "y"` stay whole, since the schema is public and an operator acts on the name; a value after any other word (user, role, database, host), a single-quoted value and a longer or upper-case name are still removed, and a kept name still goes through the later removals and, of any length, is removed when it equals a configured secret, the value of a setting named as a credential, the user, password or host of a configured address or the database a database address names, the value of any database setting (`POSTGRES_*`, `PG*`, the database user and database names among them), or the database host whole or by label: `isConfiguredName` in `oracle/src/requestSecrets.js`), and only then caps it at `MAX_DESCRIBED_LENGTH` (300), so a cut never leaves part of a secret; a revert's data and ` (cause: KIND)` (the cause's code or name, never its message) are added after. Network peer details are never kept (`oracle/src/networkPeers.js`): whatever Node writes after a network error code (`connect ECONNREFUSED`, `getaddrinfo ENOTFOUND`, …), the host and certificate names of a TLS error, the host the database client quotes, `port N`, IPv4 and IPv6 addresses with or without a port, and a dotted host with a port go, while the code and the system call stay; a stack frame (`x.js:10:5`) is kept, and a host name written alone outside these shapes is not recognised. `describedError(error)` gives an Error object with that message, the original frames (only lines shaped as a frame, read after the lines of the original message, so a message line that starts with `at` is not taken for one) and code, and the original's name only when it is one short word (else `Error`); none of the original's `address`, `port`, `hostname` or `host` fields come along. A payload that decrypts but does not parse is reported by kind only: a parse error's message quotes the start of the user's text. Two things are kept on purpose: a revert's data (the contract's answer, read from the chain) and a host and path written without a scheme, which is not taken for an address; the secret parts of configured addresses are removed from it by value. `sendAlert` and the Sentry scrubber remove addresses and network peers from all text they are given as well, so a missed call site cannot send one out, and Sentry is sent each exception's message (the error's own and each linked cause's) as `describedText` writes it, a model provider's error as its type alone (`scrubbedEvent` in `oracle/src/sentryInit.js`; `oracle/test/sentryErrorEvents.test.js` runs the real SDK on such errors). What the framework prints is cleaned at every level (`cleanedFrameworkArgs` in `oracle/src/elizaos/mutedFrameworkLogs.js`), through both of its loggers: the shared one, wrapped where the oracle loads it, and the agent runtime's own, which the runtime builds in its constructor (`this.logger = createLogger(...)` in `@elizaos/core` 1.7.2) as a plain property and which the oracle replaces with a cleaned one (`cleanRuntimeLogger`) once the runtime is built and before it is started; the start fails if it cannot be replaced. A line of text and a text element of a list are printed as `describedText` writes them (their first line, without a failed query's text and values, addresses, secrets, peers and quoted values), and an error object as its description. A structured line keeps only its numbers, flags, the fields that name a part of the system (`src`, `serverName`, `toolName`, `extension`) and an error field (`error`, `err`, `errorMessage`) as its description; every other text field (the start of the model's reply the runtime warns with when it cannot read it, an answer, a message's content) and anything nested is dropped. `oracle/test/runtimeLogger.test.js` builds a real runtime in a child process and reads what it prints, and pins the framework's property and its warning call, so an upgrade that changes either fails there. The oracle also holds the framework at `warn`: `aiAgentOracle.js` loads the env files and then sets `LOG_LEVEL` (`oracle/src/elizaos/frameworkLogLevel.js`) before it first loads the framework, which reads it once; a level the operator set at `warn` or stricter is kept, and a looser or unknown one (read by the framework as info) is replaced. `compose.yaml` and `compose.base-testnet.yaml` still say `LOG_LEVEL=info` (a compose file's environment block is generated from the env files): in the TEE that is replaced with `warn`, so the level those files show is not the one that takes effect. Its information and debug lines, which are many and can carry a query's text, its values and a peer, are not printed; warnings and errors are, cleaned. `oracle/test/frameworkLogLevel.test.js` loads the oracle module in a child process, builds a runtime and reads what each level prints. The stored `last_error` of a failed retry is the description too. A provider request that got no usable answer while an event was being handled (`isTransientProviderError` in `oracle/src/errors.js`: ethers `SERVER_ERROR`, `TIMEOUT`, `NETWORK_ERROR`, `UNKNOWN_ERROR`, `NONCE_EXPIRED`, `REPLACEMENT_UNDERPRICED`, and a `CALL_EXCEPTION` with no revert data whose JSON-RPC error message does not speak of a revert) queues the event for retry; it is never the fatal branch. When that happens on the first `isJobFinalized` read of a prompt or regeneration, the handler stops there, before any model or storage spend. A start-up that fails is printed, reported and ends the process (`oracle/src/index.js`). A request described in parts has no address to find (a span named `POST /v2/<key>`, a query string), so two more things hold: Sentry records nothing about the oracle's own outgoing requests (no span, no breadcrumb, no trace header; `outgoingRequestIntegrations` in `oracle/src/sentryInit.js`), and the secret parts of every configured address (a long path segment, a query value, a password) are removed by value wherever text is scrubbed (`oracle/src/requestSecrets.js`, applied by `withoutAddresses`). `oracle/test/sentryOutgoingRequests.test.js` runs the real SDK against such an address and reads what would be sent.

**Oracle role.** Every submission needs the oracle role on the agent (`isOracle(address)`; the owner grants it with `addOracle`). The oracle never exits for want of it (`oracle/src/oracleRoleGate.js`). At start-up on EVM it pages once ("CRITICAL: Oracle Not Authorized", naming the `addOracle` call) and carries on booting, heartbeat included; every step that would answer a prompt (`handleAndRecord`, the poll loop, the catch-up scan, the retry pass) waits at the gate. While running, a refused submission is confirmed with `isOracle` before the role is treated as lost: revert data naming `UnauthorizedOracle`, or a revert at mining time that carries no reason (`lostOracleRole`). The event is then queued for retry instead of dropped, and a retry that hits the missing role is not counted as a failed attempt. While waiting it asks the chain every 30 s, pages again each hour ("CRITICAL: Oracle Still Not Authorized"), and sends "Oracle is authorized again" when it resumes. On Sapphire the ROFL app registers itself at start-up, so a role lost while running needs a restart. Prompts older than the refund timeout are still refunded by the escrow. Start-up settles where to resume from before the first wait, and with no stored cursor it stores that block at once, so prompts submitted during a wait are scanned however long the wait lasts. That also holds across a restart during the wait, provided the store accepted the write and the chain is older than the look-back.

**Encryption key on chain (EVM agent).** `oracleEncryptionKey()` is the key clients encrypt a prompt's session key to, and `oracleEncryptionKeyPublisher()` is the oracle that published it. Only an address with the oracle role can publish, through `setOracleEncryptionKey(key, proof)`: the key is 65 bytes uncompressed and the proof is a signature made by that key over a fixed domain string, the chain id, the agent address, the sender and the key (EIP-191), so the only key that can be published is one whose holder signed for an address with the oracle role. The proof says who holds the key, not where it was made: the owner still decides which addresses are oracles. A key can be published when none is, or replaced by its own publisher; another oracle's key cannot be replaced, and publishing the key already there, with a valid proof, is a no-op for any oracle. When the publisher loses the role (`removeOracle` or `renounceRole`) the key is withdrawn and `OracleEncryptionKeyUpdated(address(0), "")` is emitted: removing the publishing oracle leaves clients with no key until another oracle publishes. The oracle does not call the setter yet; that is a later change. On Sapphire the setter stays TEE-only with no proof, and only the event shape matches.

### AI Routing Hierarchy

`classifyIntent()` (`oracle/src/geminiDirect.js`) classifies the intent with a direct Gemini small-model call (JSON-constrained; any failure routes to MARKET), then dispatches:

1. **TRADABLE path** — `queryTradableAssistant()` calls the 1st-party Firebase Callable (SenseAI backend)
2. **ELIZAOS path** — `queryElizaOS()` uses the ElizaOS character + senseai plugin defined in `oracle/src/elizaos/`
3. **ChainGPT fallback** — `queryChainGPT()` if primary paths fail
4. **Direct Gemini final fallback** — `queryGeminiDirect()` calls Gemini without the agent runtime if ChainGPT also fails (a different failure domain from the ElizaOS path, which fronts Gemini through plugin-google-genai)

**Market-data tool server (`oracle/src/elizaos/coingeckoToolServer.js`).** The ElizaOS path gets CoinGecko data through an MCP server the oracle starts as a child process. It is the dependency `@coingecko/coingecko-mcp` at one exact version, so it is in `bun.lock` and in the image, and the oracle's own node runs the package's entry file from `node_modules`: nothing is fetched from a registry at run time. The version is 2.5.0 on purpose. It offers fixed tools (`get_simple_price`, `get_coins_markets`, …), each a read from CoinGecko; releases from 3.0.0 replace them with one tool that runs code written by the model in a Deno runtime the image does not have. Two things in 2.5.0 stay off: its own code tool (off unless an option asks for it; it would send the model's code and the CoinGecko key to a third party) and the documentation search (turned off with `--no-tools=docs`; it would send text chosen by the model to a third party). `oracle/test/coingeckoToolServer.test.js` starts the installed server and holds all of this, along with the rule that every tool server in the character is started by node from an installed package. To move the pin: change the version in `package.json` and in that test, run the test, and read what the new release changed. The child is given its CoinGecko key and environment name, `PATH`, and the MCP library's own defaults (`HOME`, `USER`, `SHELL`, `TERM`, `LOGNAME`); none of the oracle's secrets. A missing package stops the oracle at start-up. With no `COINGECKO_API_KEY` the server starts and every call fails for want of a key.

**Agent settings (`oracle/src/elizaos/agentSettings.js`).** The agent framework copies environment variables into the character's settings when the agent is added, and writes the character to the agent database when the agent starts. With no list it copies every variable. `AGENT_ENV_ALLOW_LIST` is that list, set before `addAgents` by `startAgentWithCleanSettings` and in no other way: model names and the framework's own tuning values, and a test refuses a name that looks like a credential or a service address. The framework's plugins read settings through the runtime and never from the environment, so what the list keeps out and a plugin still needs is handed to the runtime as its own settings, which it keeps in memory and does not store: `agentForFramework` takes the tool servers (`mcp`) out of the character and passes them, with `POSTGRES_URL` and `PGLITE_DATA_DIR` for the database plugin, as the agent's `settings` in `addAgents`. The character keeps an empty `mcp` block in their place: on a start the framework puts stored settings under the character's own and the tool plugin looks in the character before the runtime, so a name left out would let a stored block choose the command the oracle runs. Tests build the framework's runtime and check that both are found, neither is in the character, and a stored block does not override. A plugin of ours that needs a credential reads it from the environment itself. `startAgentWithCleanSettings` is the only place the oracle adds and starts its agent, and it owns the order: clean, set the list, add, start, clean again. Tests call it with stand-ins, so a step that is skipped or moved fails a test. The clean (`cleanStoredAgentSettings`) so runs twice, before the agent is added and after it has started, and removes from every row of `agents` any stored value whose name is not on the list, any stored tool servers, and any setting under a name the character does not define itself (the framework reads a stored setting ahead of the one handed to the runtime). The framework merges stored values back in on every start, so not copying is not enough; the clean before the start keeps what an earlier build stored out of the running agent, and the one after removes what the start itself wrote. Rotate a credential an earlier build stored once a start-up line shows the clean ran. A failed clean is alerted with the kind of error only and does not stop the oracle. The clean waits for its alert for at most ten seconds: only the first clean of an old row has anything to report, so a start that stops soon after must not leave before the alert is out, but the clean runs before the oracle starts on its events and must not hold them up. Where no agent database is configured it says so and does nothing. To give the framework a new setting, add its name to the list; never add a credential. A new framework plugin that reads a setting with no environment fallback gets it through `agentForFramework`.

**Tool server watch (`oracle/src/elizaos/toolServerWatch.js`).** The framework's MCP service connects the character's tool servers and calls their tools, and on its own tells the oracle nothing it can act on. `initializeEliza` points the watch at the agent after the agents start (`follow`) and does not wait for it: the service counts as started only after it has tried every server, which can take minutes. A service not started after three minutes is alerted as missing, and is still attached to when it arrives. When the service has started the watch prints `[ToolServer] <server> connected, N tools`, and sends `CRITICAL: Market-data tool server unavailable` when a server is not connected, does not offer a tool the answers rely on (`oracle/src/elizaos/marketDataTools.js`), or connected only after the agent was shown its tools (the framework builds that list once; the alert says to restart). The oracle still starts, because only some answers need these tools. It wraps the service's tool call and sorts each call into one of four outcomes. `ok`. `failed`, which is thrown as `ToolCallFailedError` so the error is never handed to the model as data: any status but the three below, the server's own words for not reaching its provider, and a call that threw. `refused` (400, 404, 422, or thrown back as invalid): the request was wrong and not the server, and the model is given the result as before. `unclear`: an error with no status, most often a filter the model wrote that the server could not run; the model is given it too. If the service cannot be wrapped at all, the watch sends `CRITICAL: Market-data tool calls are not being watched`. Every call prints one line with the server, the tool and the outcome. Nothing a tool or the model wrote is printed, thrown or alerted by the watch: the model writes a call's arguments from the user's prompt, and a tool's error text can repeat them. An outcome is worded by the watch, and a tool's name is printed only when the server offers a tool of that name. The MCP plugin's own lines that carry the model's arguments, its reasoning or a tool's output are hidden by `oracle/src/elizaos/mutedFrameworkLogs.js`; that covers the plugin, which uses the framework's shared logger; the agent runtime's own logger is held at `warn` (above). `queryElizaOS` prints the length of each emission, not its opening. Alerts about calls, at most one in ten minutes: `CRITICAL: Market-data tool calls are failing` after five failed calls in a row or ten of the last twenty (a key that stopped working fails every call while the server stays connected), and `CRITICAL: Market-data tool calls are being refused` after ten refusals since a call was last answered (a key of the wrong kind). A server that was fine and no longer is sends `CRITICAL: Market-data tool server lost` once, after a second look 30 seconds later, again if what is wrong with it changes, and its return is printed at warning level. The watch looks at the servers every minute, after every failed call, and on every heartbeat. The heartbeat carries `toolServers` (`observe()` in `toolServerWatch.js`, read by `oracle/src/oracleVitals.js`): `{ servers: { <name>: { status, tools, usable } }, calls: { ok, failed, refused, unclear }, rejectedRuns: { toolError, noTool, unreadable } }`, where `usable` is false for a connected server the agent cannot use and the counts are cumulative. When a tool step fails, the MCP plugin replies with an apology (`toolError`), or says it has no tool (`noTool`), or asks the user to repeat the request because the model's choice could not be read (`unreadable`); `toolFailureKind` (`oracle/src/answerSelection.js`) recognises each by the thought sent with it. Such a reply is never the stored answer and its thought is kept out of the stored reasoning. A run that has one is rejected by `queryElizaOS` with `UnansweredToolFailureError` and counted in `rejectedRuns`, unless a synthesis of ours answered, or the plugin wrote from a tool's result after the last failure; a plain reply after the failure does not count, because the framework's closing reply is written from the failed step. `queryAIModel` then answers with the direct Gemini call and does not ask ChainGPT, which keeps its own record of the conversation outside the TEE. `COINGECKO_API_KEY` is required at start-up on every network that is not local, and the example file's placeholder counts as missing.

### Decentralized Storage Layer (`oracle/src/formatters.js`)

Conversation data is uploaded to Autonomys (`@autonomys/auto-drive`), or to Irys/Arweave when `STORAGE_PROVIDER=irys` (`oracle/src/storage/storage.js`); reads take either kind of id. File types:

- `ConversationFile` — created once per conversation, stores metadata
- `MessageFile` — one per message; contains `parentCID` linking to prior message (linked-list for history reconstruction). An assistant file also has `sources` and `reasoning` (each item with its `attempt`, 1 for the first tier tried), optional `reasoningDuration`, and optional `answerAttempt`, the attempt that produced the answer, written only above 1 (a fallback tier answered); items with a lower attempt belong to earlier attempts
- `ConversationMetadataFile` — updated on metadata changes
- `SearchIndexDeltaFile` — keyword delta for client-side search; keywords generated by `generateKeywords()` (stopword-stripped)

**Reading stored files.** A prompt names its parent message by a content id inside its encrypted payload, and each message file names its own parent, so every id the oracle reads is the user's to choose. Four things hold whatever they point at.
- **An id has a shape before it is used** (`oracle/src/storage/contentId.js`): an Autonomys id is `bafkr6i` and 52 of `[a-z2-7]`, an Irys/Arweave id 43 or 44 of `[A-Za-z0-9_-]`, a local IPFS id (`bafkrei` or `bafybei` and 52 of `[a-z2-7]`) only while `LOCAL_IPFS_API_URL` is set, and a mock id (`mock_` and 20 hex) only under `USE_MOCK_STORAGE=true`; all of them fit the dApp's rule for a content id (1 to 128 of `[A-Za-z0-9_-]`). The payload schema takes only these for `previousMessageCID`, `promptMessageCID` and `originalAnswerMessageCID`, so anything else is bad input and the event is dropped, with the field named and the value never repeated. The storage router fetches nothing for any other id, in every mode, and its error and the walk's log lines never print one (`printableContentId`).
- **Every fetch is bounded** (`oracle/src/storage/storedFileFetch.js`, `fetchStoredFile`): a byte limit counted chunk by chunk as the body arrives, a declared `Content-Length` over it refused before the body is read and one under it not trusted, and a time limit from the request to the last byte; either ends the request and closes the connection. The Irys gateway, Auto Drive and the local IPFS node all read through it. Auto Drive is read with the SDK's own download request (`sendDownloadRequest`, the same service, account and `/downloads/<cid>?ignoreEncoding=true` path as `downloadFile`, which takes no signal and would inflate a compressed file): the oracle uploads with no compression and no password, so the bytes are the file. `MAX_STORED_FILE_BYTES` is 8 MiB, above `LARGEST_WRITTEN_FILE_BYTES` (about 6.8 MiB: an assistant file with every attempt's steps at the frame limit, its sources, a 1 MiB answer, sealed); `STORED_FILE_TIMEOUT_MS` is 30 s. A caller can only tighten them, and a limit that is not a finite number is the default. Over the byte limit is `StoredFileTooLargeError`, a `BadInputError`: the oracle writes no file that size, so the event is dropped, on its first attempt or a retry, and nothing is alerted. Over the time limit is `StoredFileTimeoutError`: in a history walk it ends the walk (below); for a conversation's key file, without which nothing can be answered, the event is queued. A body sent with `Content-Encoding` is counted as it is decoded. The oracle reads nothing from the payload mirror; it only writes to it.
- **No file the oracle writes is one it would refuse to read.** `storage.uploadData` refuses any file over `LARGEST_WRITTEN_FILE_BYTES` (`StoredFileWriteRefusedError`, retryable) before a provider is asked, in every mode. A model tier whose answer, as JSON, is over `ANSWER_ALLOWANCE_BYTES` (1 MiB) counts as that tier not answering (`storableAnswer` in `aiAgentOracle.js`): the next tier is asked, and when none is left the no-answer path runs. The answer is never trimmed, so what is streamed is what is stored. The live stream's own limit is lower (64 KiB of text): an answer between the two is stored and sent without its answer frame.
- **A history walk is bounded as a whole** (`HISTORY_LIMITS` in `aiAgentOracle.js`): `AI_CONTEXT_MESSAGES_LIMIT` files (all of which reach the model; at most 100), 32 MiB read from storage or the cache, 90 s, and the messages' contents at most `contentChars` (half the messages as 5,000-character prompts and half as 64 KiB answers: 705,360 characters for 20, which no conversation of real prompts and normal answers reaches); each fetch gets the smaller of its own limits and what the walk has left. Any of these spent, a failed or timed-out fetch (a 404, a gateway error, a slow gateway, an id of the wrong shape) or a file that does not decrypt or is not a message file ends the walk, and the prompt is answered with the newer messages read so far; only a file over its own limit drops the prompt. A conversation's key file is read with a 4 KiB limit.
- **The cache holds only files that decrypted with the prompt's key and read as a message file** (a role of `user` or `assistant`, content a string or null, the parent absent, null or a string), counted by characters up to 128 MiB and 8 MiB an entry; any other file is fetched again next time. At the queue's concurrency (5) a prompt reads one file at a time, so fetches in flight hold under 5 x 8 x 8 MiB = 320 MiB at worst (each file's chunks, text, ciphertext, plaintext and parsed object); each handler's history is at most `contentChars` characters (about 1.4 MB as UTF-16) and its copies in the model request; plus the cache, on a 4 GiB machine.

### State Persistence

The chain cursor and the failed-job queue live behind one store (`oracle/src/oracleState/`):

- **Postgres** — tables `oracle_state.oracle_cursors` and `oracle_state.oracle_failed_jobs` in the oracle's own `oracle_agent` database, created at boot by the same plugin-sql migration that creates the agent tables (`agentSchemaMigrator.js`). Survives a restart and a `--wipe-storage` deploy.
- **Files** (`oracle-state.json`, `failed-jobs.json`) — only where no Postgres is configured (localnet, e2e).

The cursor only moves forward, except through the reorg rewind. A failed job is a pointer to the event (tx hash + log index); the retry re-reads the receipt. Retries are claimed under a 15-minute lease, back off exponentially (base 30s, doubles per attempt), and after 10 attempts the job is kept on record as `exhausted` with a CRITICAL alert. If the database cannot be read at start-up the oracle retries for about a minute, then falls back to a 1,800-block lookback and alerts. If the migration cannot create the tables the oracle does not boot. Failures it absorbs while running (cursor writes, queue reads, a poll loop stuck on one range) alert once when they last and once on recovery (`oracleState/outageTracker.js`).

## Environment Files

Two sets of env files, one per layer:

| Level | Files |
|-------|-------|
| Root (contracts/deployment) | `.env`, `.env.localnet`, `.env.testnet`, `.env.mainnet`, `.env.base-localnet`, `.env.base-testnet`, `.env.base-mainnet` |
| Oracle | `oracle/.env.oracle`, `oracle/.env.oracle.base-mainnet`, `oracle/.env.oracle.base-testnet` |

Oracle tests use `oracle/.env.oracle.example` (committed, safe values).

`scripts/deploy.js` on an EVM network reads `DEPLOY_MODE` (`fresh` or `upgrade`, required) and the two pair addresses from the `ENV_FILE` alone, and refuses when the root `.env` or the shell sets one the file does not: `fresh` refuses either pair address, `upgrade` needs both. A fresh pair on a live network also reads `TOKEN_CONTRACT_ADDRESS`, `TREASURY_ADDRESS`, `EXPECTED_FEE_TOKEN_SYMBOL`, the four `INITIAL_*_FEE` and `DOMAIN` from the file alone (`FRESH_LIVE_FILE_ONLY_VARS`), and needs the treasury, the symbol, `DOMAIN` and the four fees; an upgrade reads none of them, and a local network keeps the merged environment (the e2e bring-up writes only the mode, the pair, the token and the symbol to its file). Each fee is a whole number of wei in decimal digits, on every network. A fresh pair on a live network refuses a set `ORACLE_ADDRESS` wherever it is set (file, root `.env` or shell), before anything is sent: there the oracle's signer is derived from the new agent's address (`oracle/src/oracleKeys.js`), so an address set before the deploy can only be another pair's signer; the deploy wallet is the first oracle and the deploy prints the hand-over, which ends by emptying `ORACLE_ADDRESS` and `ANSWER_TX_HASH` again. On a local network `ORACLE_ADDRESS`, when set, is the first oracle instead of the deploy wallet; one that is the deploy wallet or the zero address is refused before anything is sent, dry run included. An upgrade has no dry run: `upgradePair` itself refuses `DRY_RUN=1` before anything is read. A refused value is described by its shape, never printed. Before the first proxy a fresh deploy reads the token (code, symbol, decimals) and prints the plan with each fee in wei and whole tokens; afterwards it reads the pair back (links, token, treasury, owners, oracle role, fees, symbol) at the block that mined the link (`readBackFreshPair`: it waits for a node that has that block and, on a live network, reads again after a failed or differing read before it gives up, so a load-balanced RPC node behind does not fail a correct pair) and fails naming each difference. The order of a fresh pair is in the runbook's "Fresh pair, in order".

Each oracle env file is split by the line `# === 📄 ORC BUNDLE CONFIGURATION (PLAINTEXT) ===`. `scripts/rofl-set-secrets.sh` pushes the keys above it on-chain as ROFL secrets and injects them into the compose as `${KEY:-}`; the keys below it are written into the tracked compose as plaintext. The database address (`POSTGRES_HOST`) is a secret, because the compose files are public: `rofl-set-secrets.sh` and `rofl-preflight.sh` refuse a non-empty value below the delimiter, and `rofl-set-secrets.sh` also refuses (naming the setting, never a value) a postgres address below the delimiter, any setting below it whose value holds the `POSTGRES_HOST` value, a key that is not upper-case snake case (`mcp` aside; named by its line number and whether it is above or below the delimiter, never by its text), and database settings with no non-empty `POSTGRES_HOST` above the delimiter. The check for a setting holding the host runs first, and no refusal of the set-secrets preflight prints a value: a placeholder, a quoted value or an `mcp` value is named by its setting and described by its length only (`rofl_value_shape` in `scripts/rofl-config-patterns.sh`). `rofl-init-cloud-sql.sh` stamps only a line above the delimiter. The oracle removes the database host by value from everything it prints, alerts, stores or reports, however short it is (the value of `POSTGRES_HOST` and the host of every postgres address, loopback aside; `oracle/src/requestSecrets.js`).

### The Universal Key: `answerMessageId`

`answerMessageId` is the single ID that links all four layers:
- **Contract**: returned as param index 3 of `PromptSubmitted`; used by `Escrow.finalizePayment(answerMessageId)` and `Escrow.cancelPrompt(answerMessageId)`
- **Subgraph**: `PromptRequest.id = answerMessageId`; `Payment.id = answerMessageId` (stored as `escrowId`)
- **dApp**: extracted from the `PromptSubmitted` receipt log at param index 3; used to track response polling

## Contract Test Suite

The contract tests (`bun run test` at the root; the count is in its last line) cover the full prompt lifecycle, spending limits, cancellation, refunds, and cross-contract flows. Key continuity contracts encoded as tests:

### Ownership

All four contracts hold ownership in two steps (`Ownable2StepUpgradeable` on the EVM pair, `Ownable2Step` on the Sapphire pair): `transferOwnership(next)` only offers it and emits `OwnershipTransferStarted`; the owner changes when `next` calls `acceptOwnership()`. Until then the old owner keeps every owner power, and `pendingOwner()` names who was offered. An address that cannot send a transaction therefore never becomes the owner. `renounceOwnership()` reverts with `OwnershipCannotBeRenounced`. A handover to a Safe is two transactions from two parties: the transfer from the current owner, then `acceptOwnership` from the Safe; it is done only when `owner()` is the Safe and `pendingOwner()` is zero. The owner and the pending owner live in OpenZeppelin's own storage namespaces, so an existing proxy takes this version with its owner and state kept and no offer open: `test/TwoStepOwnership.test.js` deploys the one-step implementations from `test/fixtures/one-step-ownership-implementations.json` (the compiled contracts at `fa4762a`) behind a proxy and upgrades them.
